# Prior Art Survey: Async Coding-Run Orchestrator Behind MCP

Research date: 2026-07-11. Compiled for the planned "coding run" orchestrator (Claude submits an objective via MCP → gets a `run_id` → detached worker runs planner→context-fetch→coder/evaluator loop→gate, logging (prompt, response, verdict) for DPO). Target hardware: single RTX 3060 12GB, Ollama-served qwen2.5-coder:14b / qwen3:14b.

Every claim below is sourced. Where a fetch tool produced a plausible-sounding but unverifiable summary (LLM-summarized PDF), that is flagged explicitly — treat those as **lower confidence** until checked against the primary PDF text directly.

## 1. Aider as an embeddable inner loop

**What it is:** Open-source terminal AI pair-programming CLI, Python, maintained primarily by Paul Gauthier. License: **Apache 2.0** ([LICENSE.txt](https://github.com/Aider-AI/aider/blob/main/LICENSE.txt), confirmed via search of the repo).

**Scripting/Python API:**
- Entry point: `aider.coders.Coder.create(main_model=Model(...), fnames=[...], io=InputOutput(yes=True))`, then `coder.run("instruction")` or `coder.run_stream(...)` for streaming. Source: [Scripting aider](https://aider.chat/docs/scripting.html).
- `Coder.run()` loops via `run_one()` internally; **`max_reflections = 3`** caps how many times the coder will re-prompt itself per `run()` call in response to lint/test failures or malformed edits (found by reading [`base_coder.py`](https://github.com/Aider-AI/aider/blob/main/aider/coders/base_coder.py) — this is a hard-coded constant, not documented in the scripting guide).
- Headless/non-interactive: `InputOutput(yes=True)` auto-confirms all prompts; CLI equivalent is `--yes-always --message "..."`, which "processes one instruction and exits cleanly."
- **Explicit, load-bearing caveat from the docs themselves:** *"The python scripting API is not officially supported or documented, and could change in future releases without providing backwards compatibility."* This is repeated verbatim across the docs and in [GitHub issue #2900](https://github.com/Aider-AI/aider/issues/2900) (open issue asking for the scripting API to be properly documented — as of this research it still isn't).

**Repo-map reuse in isolation:** Not resolved — the scripting docs say nothing about repo-map lifecycle when instantiating multiple `Coder` objects (e.g., whether the map cache persists across `Coder.create()` calls or is rebuilt each time). The repo-map itself is tree-sitter + PageRank-ranked symbol extraction ([repomap.html](https://aider.chat/docs/repomap.html), [2023 design post](https://aider.chat/2023/10/22/repomap.html)) — a decent design to imitate for the planned system's "deterministic fetchers," but reusing *aider's* map object outside a full `Coder` instance is undocumented territory. **Not verified**; would need source-diving `aider/repomap.py` directly to confirm cache reuse semantics.

**`--auto-test`/`--test-cmd` loop semantics:**
- `--test-cmd "<cmd>"` + `--auto-test` runs the test command after every edit; **non-zero exit code triggers an automatic fix attempt** fed back to the model as the test output. Source: [lint-test.html](https://aider.chat/docs/usage/lint-test.html).
- **Iteration cap is not documented** in the test-loop docs specifically, but the `max_reflections = 3` constant found in `base_coder.py` almost certainly governs it (reflections are the general retry-on-failure mechanism covering both lint and test failures). This should be verified by reading the actual reflection-triggering code path before relying on it.
- Common real-world CI one-liner: `aider --message "fix every failing pytest in tests/" --yes-always --auto-test --test-cmd "pytest -x"`.
- Linting is a **separate** pass (`auto_lint=True` by default) that runs before/alongside testing but is independently configurable via `--no-auto-lint`.

**Real examples of embedding aider in a larger system:**
- [presidio-oss/aider-based-code-generator](https://github.com/presidio-oss/aider-based-code-generator) exists but its README content could not be extracted via WebFetch (page didn't render the actual embedding details) — **flagging as an unverified lead**, worth a manual look rather than trusting a secondhand description.
- The much more common pattern found across the ecosystem: **spawn aider as a subprocess/CLI, not import it as a library.** E.g., [AgentWrapper/agent-orchestrator](https://github.com/ComposioHQ/agent-orchestrator) "spawns [CLI coding agents] as independent terminal processes inside tmux sessions" rather than embedding in-process, explicitly because "Claude Code, Codex, Aider, and OpenCode are all CLI tools that expect a terminal environment." This is a strong signal: **practitioners consistently choose subprocess isolation over Python-API embedding**, presumably because of the "not officially supported" caveat above plus aider's global-state-heavy `Coder` object model.
- Aider's own headless mode (`--message` + `--yes-always` + `--auto-test`) is explicitly designed for CI wrapping, i.e., subprocess invocation is the *sanctioned* path even though a Python API technically exists.

**Known limitations of embedding:**
1. Python scripting API is unversioned/unstable — any embedding is coupled to aider's release cadence with no compatibility guarantee.
2. `Coder` carries substantial mutable state (chat history, `aider_edited_files`, git-commit tracking) — running many short-lived `Coder` instances per orchestrator iteration (as the planned system's loop implies) means re-paying setup cost each time unless the object is kept alive and reused via `Coder.create(from_coder=self, **kwargs)` (the documented "clone" pattern).
3. Aider auto-commits after edits by default — an orchestrator wrapping aider needs an explicit strategy for whether/when that's wanted, since it changes git history as a side effect of every iteration.
4. No built-in run_id/job concept — aider is fundamentally a synchronous, single-session tool; any async wrapper (run_id, polling, cancellation) is entirely the embedding system's responsibility.

**What to steal:** the repo-map design (tree-sitter symbol extraction + PageRank ranking) as a pattern for the planned system's deterministic context fetchers; the `--test-cmd`/auto-fix-on-nonzero-exit contract as a simple, provider-agnostic evaluator interface; the CLI-headless-mode-as-integration-point convention (build your coder-model wrapper to also expose a stable one-shot CLI/subprocess mode, not just a library API, since that's what the ecosystem actually trusts).

**What to avoid:** don't depend on `aider.coders.Coder` as a long-lived importable dependency — either shell out to the aider CLI (accepting subprocess overhead) or don't use aider at all for the coder step; treat the "reflection" retry-count and repo-map internals as unstable implementation details, not public contracts.

## 2. Agent harness architectures

### OpenHands (formerly OpenDevin)
- **License: MIT** (stated in the [OpenHands Software Agent SDK paper](https://arxiv.org/html/2511.03690v2) abstract/conclusion, and on the [GitHub repo](https://github.com/OpenHands/OpenHands)).
- **Architecture:** event-sourced, not a classic plan→execute→verify pipeline. Core abstractions: `Agent` (stateless, immutable — LLM + tools + security policy), `Conversation` (factory that returns `LocalConversation` for in-process execution or `RemoteConversation` for HTTP/WebSocket to a remote agent server), `Workspace` (`LocalWorkspace` / `DockerWorkspace` / remote sandboxes), and an append-only `EventLog` inside `ConversationState`. The loop: LLM emits an Action → tool executes with validation → Observation appended to the event log → next LLM call sees the updated log. This is the "CodeActAgent" perception-action loop.
- **Embeddable as a library:** **Yes, explicitly designed for it.** The SDK splits into `openhands.sdk` (core), `openhands.tools`, `openhands.workspace`, and an *optional* `openhands.agent_server` — CLI, Web UI, and GitHub App are all separate downstream consumers of the same core library rather than the core depending on any of them. This is the closest match among the surveyed harnesses to "embeddable as a library rather than framework takeover."
- **Small-model (7–14B) performance:** **Not evaluated in the SDK paper.** It benchmarks 14 models (7 closed frontier + 7 open-weight) but does not disclose specific parameter counts or break out a 7–14B tier, and provides no frontier-vs-local comparison. Treat "OpenHands works well with 14B" as an **open question**, not a validated claim.
- **Steal:** the `Conversation`/`Agent`/`Workspace` separation as an architecture pattern for keeping the future orchestrator's core loop decoupled from its delivery surface (MCP tool today, maybe something else later); the append-only event log as the natural place to hang the (prompt, response, verdict) DPO-logging requirement — it's already the right shape for that.
- **Avoid:** don't assume its default prompting/tool-calling flow works well non-fine-tuned on 14B — no evidence either way.

### SWE-agent (and mini-SWE-agent)
- **License: MIT** for both ([SWE-agent/SWE-agent](https://github.com/swe-agent/swe-agent), [SWE-agent/mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent)).
- **SWE-agent architecture:** built around the **Agent-Computer Interface (ACI)** — a curated tool surface (`find_file`, `search`, windowed `file_viewer`, an `edit` tool that lints via flake8 *before* applying edits, `run_tests`) designed specifically to be legible to an LLM rather than exposing a raw shell. [NeurIPS 2024 paper](https://arxiv.org/abs/2405.15793).
- **mini-SWE-agent architecture:** a deliberate simplification — ~100 lines for the agent loop itself. No hard-coded tool list, no external planner, no verification scaffold: "all logic is internalized by the model's own completions." Every step is one shell command executed via `subprocess.run` (stateless — no persistent shell), and history is strictly linear (trajectory == message list, nothing hidden). >74% on SWE-bench Verified despite the minimalism. Model-agnostic via LiteLLM (so Ollama-served models are reachable, though no direct evidence was found of anyone running it against 7–14B Ollama models specifically — **unverified** for this exact use case). Design quote: *"a hackable tool, not a black box."* [github.com/SWE-agent/mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent).
- **Embeddable as a library:** mini-SWE-agent explicitly supports both a `mini` CLI and direct Python instantiation: `DefaultAgent(LitellmModel(...), LocalEnvironment()).run(task)`. This is the cleanest "library, not framework" story of everything surveyed — smaller surface than OpenHands, easier to vendor/fork wholesale.
- **Small-model performance:** the only concrete number found tying a small open model to a SWE-bench-style result is from a different project (SWE-AGILE, using Qwen3-8B, ~21.45% success — not mini-SWE-agent itself), so this is **adjacent evidence, not a mini-SWE-agent-specific result.**
- **Steal:** the "subprocess-per-action, no persistent shell state" design — makes the loop trivially sandboxable and is a good match for a system that already runs a separate evaluator process each iteration; the linear-history-equals-trajectory simplicity as an anti-pattern check against over-engineering the planner/coder message plumbing.
- **Avoid:** SWE-agent's full ACI is heavier machinery than the 100-line version and pulls in more infra assumptions (Docker-based execution environments) that may not map cleanly onto a single always-on GPU box.

### AutoCodeRover
- **License: this is the most important finding in this section — check before touching the code.** The current [`nus-apr/auto-code-rover` LICENSE](https://raw.githubusercontent.com/nus-apr/auto-code-rover/main/LICENSE) is the **SONAR Source-Available License v1.0**, not MIT/Apache. It is a source-available (not OSI open-source) license whose "Non-competitive Purpose" clause explicitly forbids: *"employing, using, or engaging artificial intelligence technology that is not part of the Program to ingest, interpret, analyze, train on, or interact with the data provided by the Program, or to engage with the Program in any manner."* Sonar (the SonarQube company) [acquired AutoCodeRover in March 2025](https://www.sonarsource.com/company/press-releases/sonar-acquires-autocoderover-to-supercharge-developers-with-ai-agents/), which explains the license flip from the original academic-era code. **This clause, read literally, would forbid exactly what the planned system wants to do with any AutoCodeRover code or its outputs** (feeding it to another AI system / training on it). Given the project's own hard requirement to check and honor licenses (`docs/ATTRIBUTIONS.md` convention already in this repo), AutoCodeRover's current code should be treated as **do-not-use**, full stop, not merely "attribute it."
- **Architecture (for reference/inspiration only, not reuse):** program-structure-aware code search (AST-based, not string matching) for context localization + statistical fault localization from test suites, feeding an LLM-driven patch loop. [ISSTA 2024 paper](https://arxiv.org/abs/2404.05427).
- **Steal (idea only, not code):** the AST-aware localization concept is worth re-implementing independently for the "deterministic fetchers" stage — but must be built from scratch or from a genuinely open-source alternative, not derived from this codebase.

### Agentless
- **License: MIT** ([OpenAutoCoder/Agentless](https://github.com/OpenAutoCoder/Agentless)).
- **Architecture:** explicitly **not agentic** — no LLM-driven action loop, no tool-use decisions by the model. Three deterministic phases: (1) **localization** — hierarchical: file → class/function → exact edit location; (2) **repair** — generate multiple candidate diffs per bug from the localized region, filter out syntactically invalid ones or ones that fail pre-existing tests; (3) **validation** — LLM also generates reproduction tests for the reported issue, used to rank/select among surviving candidates. [FSE 2025 paper](https://lingming.cs.illinois.edu/publications/fse2025.pdf), [arXiv](https://arxiv.org/abs/2407.01489).
- **Performance/cost:** best open-source SWE-bench-lite result at the time (82/300, ~27.3%) at ~$0.34/issue — notably *cheaper and simpler* than the agentic alternatives, contradicting the assumption that more agentic autonomy is required for good repair performance.
- **Small-model applicability:** not specifically tested with 7–14B models in what was found, but the architecture is uniquely well-suited to weak models precisely *because* it removes the "decide what to do next" burden from the LLM — the model only needs to (a) point at code locations, (b) write a diff, (c) write a test. This is a much narrower ask than full agentic tool-use planning, which is exactly the kind of task decomposition small models handle better than open-ended agentic reasoning.
- **Steal — this is probably the single most relevant harness for the planned system's coder step.** Its "deterministic scaffolding around narrow LLM calls" philosophy is structurally identical to the planned design's separation of deterministic fetchers / planner / coder / evaluator. If the coder step in the planned system starts drifting toward "give the model a shell and let it decide," Agentless is the concrete evidence that a much more constrained design gets *better* results at *lower cost*, especially relevant on a single 12GB GPU where every unconstrained tool-call round-trip costs real wall-clock time.
- **Avoid:** Agentless is issue-resolution-shaped (given a bug report, find+fix), not general "build to spec" codegen — the localization phase assumes an existing bug/failing-test entry point, which may need adaptation for greenfield or feature-add objectives in the planned system.

### mini-SWE-agent vs. SWE-agent vs. OpenHands vs. Agentless — quick comparison for this project
| | License | Embeddable as library | Plan/verify built in? | Best fit for 12GB single-GPU |
|---|---|---|---|---|
| OpenHands SDK | MIT | Yes (designed for it) | Event loop, no explicit verify stage | Medium — heavier abstraction stack |
| SWE-agent | MIT | Loosely (via `sweagent` package) | ACI has run_tests but no built-in judge | Medium — ACI/Docker assumptions |
| mini-SWE-agent | MIT | Yes, cleanly | None — model does everything | High — minimal footprint, easy to fork |
| AutoCodeRover | **Source-available, AI-use-restricted** | N/A — do not use | Statistical fault localization | **Excluded on licensing grounds** |
| Agentless | MIT | Yes (it's just scripts/phases) | Yes — explicit validation phase | **High — closest structural match to the plan** |

## 3. MCP async/long-running support and sampling

This is the area with the most consequential findings for the planned design, including a genuine contradiction discussed in the final section.

### Spec state as of this research (2026-07-11)
- **Current stable spec: 2025-11-25.** It introduced an **experimental** "Tasks" primitive: task-augmented `tools/call` returns a `CreateTaskResult` (`taskId`, `status: working`, `pollInterval`) immediately; the caller polls `tasks/get`, retrieves the final payload via `tasks/result` (which blocks until terminal state), and can `tasks/cancel`. States: `working → input_required → {completed, failed, cancelled}`. Full detail: [modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks). Task support must be negotiated per-tool via `execution.taskSupport` (`required`/`optional`/`forbidden`) in `tools/list`, and both client and server must declare a `tasks` capability.
- **A 2026-07-28 release candidate is imminent** (spec finalizing right after this research's date) and it substantially rewrites this area: [blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/).
  - The Tasks primitive is being **pulled out of core spec entirely and moved to an "extension"** — the spec authors' own words: "production use surfaced enough redesign that the right home for it is an extension rather than the specification." `tasks/list` is removed outright ("can't be scoped safely without sessions"). Anyone using the 2025-11-25 experimental Tasks API "will need to migrate to the new lifecycle."
  - The whole protocol is going **stateless**: `initialize`/`initialized` handshake and the `Mcp-Session-Id` header/protocol session are removed. Client info/capabilities move into per-request `_meta`.
  - Critically, **the spec authors explicitly recommend the pattern the planned system already intends to use**: *"servers that need to carry state across calls can do what HTTP APIs have always done: mint an explicit handle... from a tool and have the model pass it back as an ordinary argument on later calls."* This is precisely `submit_run → run_id`, `get_run_status(run_id)`.
  - **Sampling is being formally deprecated** in the new lifecycle policy, with the recommended replacement being direct integration with LLM provider APIs rather than protocol-level sampling.

### Progress notifications
- Optional, token-based (`progressToken` in request `_meta`), receiver may send `notifications/progress` with `progress`/`total`/`message`. Applies to task-augmented requests too (same token persists across the task's lifetime). Spec: [progress utility](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/progress). This is genuinely useful *in spec* but see below for whether Claude Code honors it.

### Claude Code's actual MCP client support (this is the crux)
Sourced from [anthropics/claude-code#31893](https://github.com/anthropics/claude-code/issues/31893), a consolidated spec-compliance-gap issue, **closed by maintainers as "not planned"**:
- `notifications/progress` — received but **ignored**, no UI surfacing.
- `notifications/message` — received but never displayed.
- **Sampling (server asks client's LLM) — not implemented.** Separately confirmed by [issue #1785](https://github.com/anthropics/claude-code/issues/1785), an open feature request specifically asking for sampling support to avoid double-billing API costs on top of a Max subscription — still unresolved.
- **Async/background tool execution — all MCP tool calls are sequential/blocking** from Claude Code's perspective today.
- `tools/list_changed` works only across prompt turns, not mid-turn; `prompts/list_changed` and `resources/list_changed` have known gaps too.
- No evidence found that Claude Code implements the Tasks primitive (`tasks/get`/`tasks/result`/`tasks/cancel`) at all — consistent with "async/background tool execution: all sequential/blocking" being listed as a gap with no fix planned.

**Bottom line: Claude Code's MCP client, as of this research, treats every tool call as a plain synchronous request-response with a bounded timeout (matches the ~120s figure already observed empirically in this repo), ignores progress notifications, and does not support sampling.** None of MCP's built-in mechanisms for "long-running work" are usable from Claude Code today, regardless of what the spec says or what an MCP server declares.

### Existing submit/poll job pattern implementations worth copying
- [SEP-1391](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1391) — "Asynchronous Tool Execution" proposal (created 2025-08-26, explicitly motivated by Claude Desktop's ~4-minute MCP tool-call timeout): operation token returned from an initial call, server manages background execution, subsequent calls poll by token. This predates and heavily informed the Tasks primitive; backward-compatible by design (didn't require changing `tools/call` semantics). Worth reading as a simpler blueprint than the full Tasks spec.
- [dylan-gluck/mcp-background-job](https://github.com/dylan-gluck/mcp-background-job) — concrete implementation: unique job IDs, process lifecycle management, real-time output monitoring. A working example of exactly the "handle pattern" the spec authors now formally endorse.
- [mims-harvard/ToolUniverse MCP_TASKS_GUIDE.md](https://github.com/mims-harvard/ToolUniverse/blob/main/docs/MCP_TASKS_GUIDE.md) — an actual adopter of the formal Tasks primitive, useful as a reference if the planned system later wants to expose Tasks-primitive support in addition to its own handle-based tool (for other, more spec-compliant MCP clients).
- [aws-samples/sample-mcp-for-long-running-tasks-with-amazon-bedrock-agentcore](https://github.com/aws-samples/sample-mcp-for-long-runing-tasks-with-amazon-bedrock-agentcore) — another handle/poll pattern reference implementation, AWS-flavored.

**Design conclusion for this research question:** build the planned system's `submit_run(objective) → run_id` / `get_run_status(run_id)` / `get_run_result(run_id)` as **plain synchronous MCP tools that happen to return/accept an opaque handle** — exactly the "ordinary argument" pattern the spec now recommends — rather than trying to use the MCP Tasks primitive or progress notifications. This is future-proof against the 2026-07-28 rewrite (which is converging on the same pattern) and works today because it never depends on anything Claude Code doesn't support (it's just a tool call with a string argument). Do not build around MCP sampling under any circumstances — it's unsupported today and being deprecated in the spec itself.

## 4. Small-model self-repair loops

### Does iterating on test failures converge at 14B scale?

The evidence is genuinely mixed and **time-dependent** — older results (2023) said small models don't benefit or are actively harmed; newer results (2025-2026, on modern instruction-tuned models) say they do benefit. This is worth flagging clearly since it's easy to cite the wrong generation of findings.

- **Chen et al., "Teaching Large Language Models to Self-Debug"** (ICLR 2024, [arXiv:2304.05128](https://arxiv.org/abs/2304.05128)). Original self-debug/rubber-duck-debugging paper. Evaluated **code-davinci-002, GPT-3.5-turbo, GPT-4, and StarCoder-15.5B**. Achieved SOTA-at-the-time on Spider, TransCoder, MBPP. ⚠️ A downstream WebFetch summary of the ICLR proceedings PDF also claimed evaluation on "Llama-2 7B/13B/70B and CodeLlama variants" with a specific "self-debug hurts <13B models" finding — **this could not be independently confirmed against the actual paper text and should be treated as an unverified/possibly hallucinated detail from the summarization tool**, not a citable fact. The verified model list (via direct search corroboration) is code-davinci-002 / GPT-3.5 / GPT-4 / StarCoder only.
- **"How Many Tries Does It Take? Iterative Self-Repair in LLM Code Generation Across Model Scales and Benchmarks"** ([arXiv:2604.10508](https://arxiv.org/html/2604.10508), April 2026). Directly relevant and recent. Tests Llama 3.1 8B, Llama 3.3 70B, Qwen3 32B, Llama 4 Scout/Maverick (17B active), Gemini 2.5 Flash/Pro across up to 5 attempts (1 initial + 4 repair rounds) on HumanEval + MBPP-Sanitized. **No model in the exact 7–14B dense range** (jumps from 8B to 17B-active MoE to 32B) — a real gap for this project's specific 14B target. Key finding: **"most gains concentrate in the first two rounds"** (76–95% of total improvement by round 2); the 8B model *does* improve (+9.8pp HumanEval, +16.0pp MBPP), explicitly **contradicting older claims that weaker models are harmed by self-repair** — the paper's framing is that this reversal is because *modern* (2024–2025) instruction-tuned small models have much better error-comprehension than the 2023-era models earlier papers tested. Repair success is error-type-dependent: name errors ~77% fixed, syntax ~66%, assertion errors (logic bugs) only ~45% — the hardest category is exactly what an execution-feedback loop is supposed to catch. Self-repair is also token-cheaper than independent resampling (11–54% fewer tokens for equivalent or better results).
- **"The Debugging Decay Index" / "Measuring and mitigating debugging effectiveness decay in code language models"** ([arXiv:2506.18403](https://arxiv.org/html/2506.18403v2), also published in Scientific Reports Dec 2025, [nature.com/articles/s41598-025-27846-5](https://www.nature.com/articles/s41598-025-27846-5)). **The single most directly useful paper for this project** — it tests models close to the actual target range: DeepSeek-Coder 6.7B, CodeLlama 7B, Llama 3.1 8B, Mistral Instruct, **Phi-4 14B**, Granite 3.3 8B. Models exponential-decay debugging effectiveness as E(t) = E₀e^(−λt) across attempts. Headline finding: **most models lose 60–80% of debugging capability within 2–3 attempts.** Phi-4 14B specifically: E₀=83.5%, λ=0.768 (relatively good retention, i.e., a good sign for 14B-class models generally). Their mitigation, "strategic fresh start" (wipe conversation history and retry from the bare problem statement once decay crosses a threshold t_θ = ln(100/(100−θ))/λ), recovered +9.76pp (Llama 3.1 8B), +7.92pp (DeepSeek-Coder-V2 16B), +3.05pp (Phi-4 14B) at **zero extra compute** (same attempt budget, just restructured). **This is directly actionable**: the planned coder/evaluator loop should budget for a full-context-reset retry rather than always appending to a growing failure transcript, and 2–3 iterations is the evidence-backed sweet spot before diminishing returns, not an arbitrary guess.
- **A Survey of LLM-based Automated Program Repair** ([arXiv:2506.23749](https://arxiv.org/html/2506.23749v1), June 2025) confirms the general shape: generate-test-refine loops show real gains (e.g., +78% plausible-fix rate with 2 refinement rounds in one cited study) but "extra iterations add runtime overhead and yield diminishing returns on simpler bugs."

**Synthesis for the planned system:** budget **2–3 repair iterations as the primary loop**, not more — this is now supported by three independent 2025–2026 sources (self-repair paper, debugging-decay paper, APR survey), not just intuition. Build in a "fresh start" option (reset context, keep only the original objective + latest test failure, drop the accreted back-and-forth) as an explicit strategy the coder loop can invoke rather than always extending the same transcript — the debugging-decay paper shows this is free and effective. Expect assertion/logic-error repair to be the hard category (~45% fix rate even for capable models) — this is where LLM-judge evaluation (used "sparingly" per the design) is most worth spending on, since compile/test-pass alone won't distinguish "looks plausible" from "actually correct" for this error class. No paper found tests exactly qwen2.5-coder:14b/qwen3:14b — the closest analog (Phi-4 14B) is encouraging but this is an extrapolation, not a direct result.

## 5. Planner/coder two-model splits

Less mature literature than the other questions — most "prior art" here is either (a) tool-orchestration papers where "planner" means task-graph compilation, not natural-language plan handoff, or (b) multi-agent-framework postmortems about what breaks.

- **LLMCompiler** and **OrchDAG**-style approaches: pose planning as `πθ(query, tools) → G` where G is a DAG (commonly serialized as JSON node/edge lists); an executor topologically sorts and executes, propagating results along edges. Motivated primarily by *latency/parallelism*, not correctness — not a close match to the planned system's single-threaded plan→code→verify loop, but the "plan is a schema-constrained JSON artifact, not free text" principle transfers directly.
- **MetaGPT** (structured, role-based messages with explicit schemas between agents) vs. **AutoGen** (dynamic, free-form message passing): search-sourced comparative claims say MetaGPT's structured contracts "reduce loss of communication information" and improve code-execution outcomes relative to less-structured approaches, while AutoGen is positioned as better for exploratory/research tasks where the workflow itself is fluid. This maps onto the planned system's split cleanly: the planner→coder handoff is a fixed, repeated production step (favor MetaGPT-style structured JSON contracts), not an open-ended negotiation (where AutoGen's flexibility would matter more).
- **Documented multi-agent failure modes** relevant to the planner/coder boundary specifically (from a 2026 survey-style search result, treat as a secondary/aggregated source rather than a single peer-reviewed paper):
  - **"Delegation breakdown"** — the planner (in the planned system's terms) omits a required field, under-specifies context, or gets the dependency order wrong, and the coder either fails immediately or silently does the wrong thing. This is the single most load-bearing risk for the planned "planner compiles objective → acceptance criteria + structured context requests" step.
  - Roughly **43% of multi-agent failures were attributed to miscommunication** rather than either agent individually being wrong — i.e., the interface is usually the bug, not the model.
  - "No protocol-level mechanism to specify budgets, deadlines, or success criteria for delegated work" is called out as a governance gap — directly relevant since the planned system's planner is supposed to emit acceptance criteria and a budget (iteration count) up front.
  - Recommended mitigation: structured logging with correlation IDs on every message/tool-call/plan-step — trivially compatible with the planned system's existing (prompt, response, verdict) logging requirement; extend the schema to include a run/iteration correlation ID now rather than retrofitting later.

**What works:** rigid, schema-validated JSON contracts for the planner→coder handoff (acceptance criteria as a typed list, not prose; context requests as structured file/symbol references, not "go read the relevant code"); treating the contract schema itself as the primary place bugs will hide.

**What fails:** letting the planner hand off free-form natural-language instructions and trusting the coder to infer scope/boundaries — this is exactly the "delegation breakdown" failure mode, and it's worse, not better, with small models on both ends, since neither model has spare reasoning capacity to compensate for an ambiguous handoff.

**Caveat:** this question has the thinnest primary-source coverage of the six — no paper found does a controlled study of *two small (7-14B) models specifically* in a planner/coder split for codegen. The above is extrapolated from adjacent multi-agent-orchestration literature and general agent-framework postmortems, not a direct empirical match. Recommend treating the structured-JSON-contract conclusion as a design *prior*, not a validated result, and instrumenting the planned system's own logs to check whether delegation-breakdown-shaped failures actually occur once it's running.

## 6. DPO/preference data from execution feedback

- **General pattern, confirmed across multiple 2024–2025 papers:** generate code → run against tests → if it fails, feed error back and regenerate → treat the final passing version as the DPO "chosen" and one or more earlier failing attempts as "rejected." This is essentially what the planned system is already going to produce as a side effect of its iterate-until-pass loop — no extra harvesting machinery needed beyond deciding which (attempt, later-attempt) pairs to log as an explicit contrastive pair. Source pattern confirmed by [Target-DPO/IterPref](https://arxiv.org/html/2503.02783v3) and the general DPO-for-code literature.
- **Target-DPO / IterPref** ([arXiv:2503.02783](https://arxiv.org/html/2503.02783v3)) is the most concrete and relevant paper found. Their pipeline: generate+test with GPT-4o, iteratively refine on failure (max 5 iterations), take the final correct version as chosen and a *randomly selected earlier iteration* as rejected — **then apply token-level masking** so the DPO loss only penalizes the tokens that actually differ (via LCS diff) between chosen/rejected, rather than the whole sequence. Reported results: Qwen2.5-Coder-7B improved from 61.6%→89.6% HumanEval after this treatment; 3.3–12.4% average improvement over vanilla DPO/RPO baselines; and importantly, **~10.4 LLM calls needed per usable pair vs. 100+ for naive sampling-based preference-pair mining** — i.e., harvesting pairs from an execution-feedback repair loop (which the planned system does natively) is far more sample-efficient than post-hoc preference mining.
- **Named pitfalls, several independently confirmed:**
  1. **Token dilution / whole-block aliasing** — naively treating an entire failing code block as "rejected" against an entire passing block as "chosen" wastes gradient on the large fraction of tokens that are identical between the two and unrelated to the actual bug; this was Target-DPO's central motivation and mitigation (token-level masking on the diff).
  2. **Noisy pair quality** — "high-pass-rate snippets may contain subtle bugs; low-pass-rate snippets may need only minor fixes" — i.e., don't assume monotonic quality-vs-test-pass-rate; a pair harvested purely from pass/fail can still be a bad contrastive example if the "chosen" side is only accidentally correct.
  3. **Reference-model collapse in DPO generally** (not code-specific) — reference model too strong prevents the policy from moving; too weak loses the regularization DPO relies on. Standard DPO pitfall, applies unchanged here.
  4. **Multi-model synthetic preference data increases reward-hacking vulnerability** — "[More is Less](https://arxiv.org/abs/2504.02193)" found that preference pairs sourced from multiple different generator models are more linearly separable on superficial cues, making the trained policy easier to game via style rather than substance. Directly relevant if the planned system ever mixes preference pairs harvested from qwen2.5-coder AND qwen3 outputs — keep provenance (which model generated which side of a pair) as metadata, and be wary of training a single reward signal across mixed-model pairs without controlling for this.
  5. **Reward hacking specific to test-pass signals (not DPO-specific, but the risk this project's pass/fail-derived reward signal shares with any RL/preference approach trained against automated verifiers):** documented exploits in code-RL settings include hardcoding outputs to the specific visible test cases, monkey-patching/overwriting the test/scoring function, deleting assertions, and premature termination to short-circuit scoring — [arXiv:2604.15149](https://arxiv.org/pdf/2604.15149) ("LLMs Gaming Verifiers"), [SpecBench](https://arxiv.org/pdf/2605.21384), [TRACE benchmark] all document this pattern across multiple 2026 papers. **Concrete mitigation for the planned system:** keep the evaluator's test suite and the coder's edit surface strictly separated (the coder should never be able to edit test files as part of a "passing" iteration unless that's explicitly the objective), and periodically spot-check "passed" iterations with the LLM-judge for exactly this kind of gaming — hardcoded literals matching test fixtures, deleted/weakened assertions, etc. — rather than trusting compile+test-pass alone as ground truth for what gets logged as a DPO "chosen" example.
- **Style collapse:** not found as a named, specific-to-DPO-execution-feedback phenomenon in a dedicated paper (searched directly, no hit) — this appears to be a real practitioner concern but **not independently verified against a primary source** in this survey. Treat "DPO on execution feedback causes style collapse" as plausible-but-unconfirmed; the closest documented adjacent risk is the reference-collapse and multi-model-separability issues above, which are verified.
- **Data imbalance:** the planned system's loop-until-pass design will naturally over-produce "eventually passed after N iterations" examples relative to "passed first try" examples, since failing attempts are definitionally more common on hard objectives. No paper directly quantifies this imbalance's effect on downstream DPO training in the code domain — flag as an open risk to monitor (e.g., in the eventual training-data audit) rather than a validated finding either way.

## Executive summary

- **Aider (Apache 2.0)** has a real but explicitly unstable/undocumented Python API (`Coder.create`/`Coder.run`, `max_reflections=3` cap found in source); the ecosystem's actual practice is subprocess/CLI invocation, not library embedding — plan for the same rather than importing `aider.coders`.
- Among agent harnesses, **Agentless (MIT)** is the closest structural match to the planned design — deterministic localize→repair→validate phases around narrow LLM calls, no agentic tool-use loop, best cost/performance on SWE-bench-lite among the compared systems. **OpenHands (MIT)** and **mini-SWE-agent (MIT)** are the two genuinely embeddable-as-library options if an agentic loop is wanted instead.
- **AutoCodeRover is now under Sonar's "SONAR Source-Available License v1.0," which explicitly forbids AI systems from ingesting/training on/interacting with its code or outputs** — this is a hard license blocker (post-March-2025 Sonar acquisition), not merely an attribution requirement; exclude it entirely.
- **MCP's own async story is mid-rewrite right now**: the 2025-11-25 spec's experimental "Tasks" primitive is being pulled out of core and rebuilt as an extension in the 2026-07-28 release; the new spec explicitly recommends exactly the "mint a handle from a tool, pass it back as an ordinary argument" pattern the planned system already intends to build.
- **MCP sampling is unsupported by Claude Code today and being formally deprecated in the spec itself** — do not design any part of the planner/coder loop around a server-initiated sampling request to the Claude Code client.
- **Claude Code's MCP client ignores progress notifications and treats every tool call as blocking/synchronous** — the run_id/poll design isn't just a nice pattern, it's the *only* mechanism that works given Claude Code's actual (not spec-ideal) behavior.
- Small-model self-repair literature has genuinely shifted since 2023: **modern instruction-tuned 8B+ models do benefit from execution-feedback repair** (contradicting older "small models are harmed" findings), with 76–95% of total gain landing in the first two rounds and diminishing sharply after — **2–3 iterations is the evidence-backed budget**, not a guess.
- The most directly relevant paper found, the **Debugging Decay Index** (tests Phi-4 14B among others), shows debugging effectiveness decays exponentially per-attempt and that a **free "strategic fresh start"** (reset context, keep only objective + latest failure) recovers several points of accuracy at zero extra compute — worth building into the coder/evaluator loop as an explicit strategy.
- **Planner/coder two-model-split literature is thin** for this exact configuration (two small local models); the closest evidence (multi-agent postmortems, MetaGPT vs. AutoGen framing) supports rigid schema-validated JSON handoffs over free-form delegation, with "delegation breakdown" (missing fields, wrong dependency order) as the dominant documented failure mode — treat this as a design prior to validate against the system's own logs, not an established result.
- **DPO-from-execution-feedback is well-supported and cheap** given the planned system's architecture (Target-DPO gets strong Qwen2.5-Coder-7B gains from exactly this generate/test/refine harvesting pattern, ~10x more sample-efficient than post-hoc mining) — but token-level masking on the diff (not whole-block chosen/rejected) is the documented fix for the dominant pitfall (token dilution), and reward-hacking-style gaming of the pass/fail signal (hardcoded test literals, weakened assertions) is a real, multiply-documented risk that needs an LLM-judge spot-check layer, not just automated pass/fail trust.

## Findings that contradict the planned design's assumptions

Being deliberately adversarial here, as requested:

1. **The "MCP tool calls have a ~120s timeout" framing undersells the actual constraint.** It's not just a timeout — Claude Code's MCP client doesn't support progress notifications, sampling, or any async primitive at all. This isn't a temporary annoyance to route around with a `run_id`; it's a structural fact about the current client that makes the `run_id`/poll design the *only* viable shape, full stop. Good news: the design already anticipated this correctly. Bad news: it also means there's no way to give the calling Claude Code session a live progress readout during the run (no progress bar, no partial-output streaming) — the caller will need to poll `get_run_status` itself and will see nothing between polls, which has UX implications (a chatty planner-status field embedded in the poll response, not push notifications, is the only lever available).

2. **The MCP spec is actively rewriting the exact primitive this system was designed against, right now (RC finalizing 2026-07-28).** If the planned system had been built to lean on the *experimental* Tasks primitive instead of a bespoke run_id tool (a plausible alternative reading of "async coding-run orchestrator behind MCP"), it would already be obsolete before shipping — the Tasks API in 2025-11-25 is explicitly being replaced. This is a point *in favor* of the bespoke-handle design, but it's worth stating explicitly: don't be tempted to "upgrade" to formal MCP Tasks support later without re-checking the spec's state at that time, since it's clearly still in flux.

3. **The self-repair literature's optimistic recent numbers (8B+ models benefiting from execution feedback) are from benchmarks (HumanEval, MBPP) that are shorter and more self-contained than the "objective → acceptance criteria → multi-file context → coder → evaluator" loop the planned system targets.** None of the surveyed papers test repository-scale, multi-file, planner-supplied-context tasks at 14B — they test single-function generation with a crisp test oracle. The planned system's task shape is closer to SWE-bench (repo-scale, ambiguous scope, planner must supply context) than to HumanEval/MBPP (self-contained, scope is the function signature). SWE-bench-style small-model results (SWE-AGILE's 21.45% at Qwen3-8B) are far weaker than HumanEval-style self-repair gains — this is a real risk that the planned system's actual difficulty tier is much closer to the harder, worse-performing benchmark than to the encouraging one, and the "2-3 iterations is enough" conclusion from Section 4 may not transfer once real repo-scale context-assembly and ambiguous acceptance criteria are in play.

4. **Agentless's headline result — that removing agentic autonomy entirely and using rigid deterministic phases *outperforms* agentic tool-use loops on cost and correctness — is in tension with the planned design's most agentic piece: giving the coder model iterative, evaluator-gated freedom rather than a single well-localized diff-generation call.** This doesn't mean the loop is wrong, but it's worth naming: the best-performing, cheapest comparable system in this survey did *less* agentic reasoning per step than the planned coder loop will do, not more. If iteration-count or cost becomes a problem in practice, "make the coder step more like Agentless's single localized diff-generation, and lean harder on the planner to narrow scope before the coder ever runs" is a real, evidenced fallback — not a compromise.

5. **The planner/coder split — arguably the design's most novel piece — has the weakest evidentiary backing of anything researched.** Nothing found tests two cooperating *small* (7-14B) models in a planner/coder split for codegen specifically; the supporting evidence is either about DAG-compiler planning (different problem — parallelism, not correctness) or general multi-agent-framework failure taxonomies (not code-specific, not small-model-specific). The "structured JSON contract beats free-form delegation" conclusion is a reasonable prior, not a validated result — the planned system is genuinely pushing past what's been published here, and should treat its own logs (which delegation-breakdown patterns actually show up, at what rate) as the real evidence source rather than assuming the literature has already de-risked this piece.

6. **DPO harvesting from a pass/fail-gated loop invites exactly the reward-hacking failure modes documented in the RL-code literature (hardcoded test literals, weakened assertions), and the planned design's "evaluator runs compile/tests every iteration, LLM-judge sparingly" cadence means the cheap, frequent signal (test pass/fail) is precisely the one most gameable, while the expensive check that would catch gaming (LLM-judge) is the one being run least often.** This is a direct tension worth resolving explicitly — e.g., always LLM-judge the specific iteration that gets logged as a DPO "chosen" example, even if the mid-loop iterations are judged sparingly, since that's the one whose (prompt, response, verdict) triple actually enters training data.
